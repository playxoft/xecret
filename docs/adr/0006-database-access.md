# 0006 — Neon PostgreSQL via Hyperdrive, accessed with Drizzle

**Status:** Accepted
**Date:** 2026-08-10

## Context

All application state lives in PostgreSQL (Neon). The Worker must reach it with low latency
and few connections, and the schema must be versioned and reviewable.

Two independent choices: **how to connect**, and **how to query**.

## Part 1 — Connection

### Options

**A. Neon serverless driver over HTTP** (`@neondatabase/serverless`)
- ✅ No TCP needed; works anywhere `fetch` exists.
- ✅ Zero setup.
- ❌ One HTTP request per query — each consuming an outgoing-connection slot from the
  6-per-invocation budget.
- ❌ No connection pooling or reuse across requests.
- ❌ Multi-statement transactions require the WebSocket mode, which is slower to establish.

**B. Cloudflare Hyperdrive + a native driver** (`postgres.js`)
- ✅ Cloudflare-recommended and measurably fastest for Neon on Workers.
- ✅ Maintains a warm connection pool at the edge — the Worker does not pay connection setup.
- ✅ Real transactions, prepared statements, native `bytea` handling (which matters: every
  ciphertext column is `bytea`).
- ✅ Does not consume the `fetch` subrequest budget.
- ❌ Requires `nodejs_compat` and a Hyperdrive binding to configure.
- ❌ One more Cloudflare resource for self-hosters.

## Part 2 — Query layer

**A. Raw SQL** — maximum control, zero abstraction; no type safety, hand-written migrations,
easy to get a `WHERE org_id = ?` clause wrong in a security-critical query.

**B. Drizzle** — SQL-shaped, types derived from schema, generated migrations, tiny runtime,
no lazy-loading or N+1 surprises. Query shape is visible in the code.

**C. Prisma** — excellent DX, but a heavy runtime with historical edge friction, and it hides
the emitted SQL. In a product where every query must provably enforce a tenancy boundary,
hiding SQL is a liability.

**D. Kysely** — very close to Drizzle. Slightly better raw query builder, weaker migration
story, no first-class schema-as-source-of-truth.

## Decision

**Neon + Hyperdrive + `postgres.js` + Drizzle ORM.**

Connection is isolated behind a thin adapter in `packages/db/src/client.ts` so that
self-hosters without Hyperdrive can switch to the Neon HTTP driver with a single environment
variable. The adapter is ~30 lines; nothing else in the codebase knows which is in use.

Migrations are generated by `drizzle-kit` and **committed and reviewed as SQL**. Generated
migrations are never applied unreviewed — a security product cannot have surprise schema
changes.

## Consequences

### Positive
- Fast, pooled database access with no impact on the outgoing-connection budget.
- Schema is TypeScript, so table and column types flow into application code automatically.
- Every query's SQL shape is visible at the call site, which makes tenancy-boundary review
  practical.
- Real transactions, needed for secret rotation and key re-wrapping.

### Negative
- Two connection paths to test (Hyperdrive and Neon HTTP). Mitigated by the adapter and by
  running the integration suite against both in CI.
- `nodejs_compat` must stay enabled, which slightly increases bundle size.
- Drizzle is younger than Prisma; some ecosystem gaps remain. Acceptable — we use a small
  surface of it.

### Rules that follow
1. **Every query touching tenant data must join or filter on a verified `org_id`.** Never
   trust an ID from the client without an ownership check — see the authorization engine in
   `packages/core/authz`.
2. Secret ciphertext columns are `bytea`, never `text`. No base64 round-tripping in the
   database layer.
3. Database credentials are least-privilege: the application role has no `DROP`, no `CREATE`,
   and no superuser rights. Migrations run under a separate role.
